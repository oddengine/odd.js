# Local recording and its download worker

R-083 keeps StreamSaver / StreamWriter and the Player / RTC recording entry points. This is a browser download, independent of server recordings, S3 uploads, playback permissions and billing.

## Setup

Serve `src/utils/utils.streamsaver.worker.js` as a dedicated same-origin worker. The Linux and Windows release scripts copy it to `release/odd.recording.worker.js` when a release is built. No build output is generated by this change. The app/player/rtc source examples import that same source from their existing `js/sw.js` entry points.

```javascript
const service = {
    script: '/sdk-recording/sw.js',
    scope: '/sdk-recording/',
    maxPendingBytes: 4 * 1024 * 1024,
    maxPendingChunks: 64,
    startTimeout: 10000,
    writeTimeout: 10000,
    flushTimeout: 10000,
};
// Pass service to Player/RTC configuration before creating media instances.
const writer = await player.record('fragmented.mp4');
writer.addEventListener(odd.events.SaverEvent.WRITEREND, function (event) {
    // srcElement is this writer, even after the media source has changed.
    console.log(event.data.outcome, event.data.error);
});
// End gracefully; normal media release does not await this local operation.
writer.close();
```

`service.enable` remains accepted, but playback setup no longer depends on download registration. Download recording registers on demand. A secure context, Service Worker, MessageChannel, cryptographic randomness and transferable streams are required. `StreamSaver.describe()` is a preliminary capability description, not proof that registration or transfer will succeed. Actual failures reject/report the operation. `isSupported(version)` retains the old semantic-version utility; the worker handshake uses a separate protocol number.

The website's Vite SDK plugin emits this exact source at `/sdk-recording/sw.js`; its media owner supplies that script and its dedicated `/sdk-recording/` scope. The worker does not cache app pages. A new random operation URL isolates downloads with identical filenames, including separate tabs; the filename is only an encoded download header. A bound MessagePort carries the handshake, and only the operation's one-use URL consumes the stream. The download iframe has a different browser client ID from its parent. Unknown operations cannot remove another operation. Version disagreement fails explicitly; it does not unregister a shared worker or restart a recording silently.

## Data and lifetime

The pending budget counts both queued and in-flight data. RTC Blob sizes are charged before conversion; Blob-to-byte conversion and writes run serially. `pendingBytes` is read-only. Internal fMP4 producers can pass a small array of byte arrays as one queued group, preserving a whole header/body pair without merging another copy. A slow callback, sink or unconsumed download fails the recording on the first byte, chunk or deadline limit; it never blocks playback or silently discards chunks and calls the file complete.

The default limits are 4 MiB / 64 pending chunks, 10 seconds from recording request through worker readiness and first valid data, 10 seconds from each enqueue to consumption, and 10 seconds from close to terminal drain. They are configurable positive safe integers. A single chunk/group exceeding the byte budget also fails. Limits describe SDK-owned queued bytes, not total browser memory or persistent storage. Browser-internal buffers and one converting Blob can add memory. On page unload, cancellation is best effort; there is no guaranteed asynchronous flush.

RTC owns its MediaRecorder and final-data listeners. Its producer adapter stops the recorder, routes final Blob events through a private tail writer, then closes the byte sink after those events have been queued. The writer never replaces its `write` or `close` methods. Capturing stream identity is fixed per operation. A late Blob cannot write into a subsequent recording. `NetStream.record(filename, ondata)` invokes the callback in order, awaiting an optional Promise with the same bounds, without creating a download worker or iframe. Completion in callback mode only proves callback processing completed.

FLV starts on a video keyframe (or the first audio sample for audio-only input), waits for all declared audio/video track configurations, writes the initialization segment once and then writes its remuxed packets. A later track absent from that initialization fails this recording. fMP4 reads recording track/default sample flags from the existing assembled moov and fragment headers. It starts at a fragment whose video first samples are independent, or an audio-only fragment, and queues complete moof/mdat groups. Sample sizes and data offsets must prove every referenced range fits the single body before any part of that group is queued; multi-mdat layouts fail explicitly rather than being truncated. An incomplete header held when the user stops is discarded before output; no partial group is reported as complete. Absolute file data offsets and unsupported track layouts fail locally rather than yielding an incorrectly relocated file. A new initialization after recording has started requires a new recording. Playback parsing/decoding is unchanged.

One recording is allowed per media instance through its terminal result; preparing/closing operations cannot be replaced by a second one. Source-generation guards stop a late worker setup from attaching to a stopped/replaced stream. End handlers compare writer identity. Writer errors affect only recording. StreamSaver.destroy stops its owner from starting work, cancels registration waits and allows already closing writers their finite drain; it does not unregister the shared worker. The final result releases the queue, producer listeners, timers, download iframe and ports. UI destruction detaches its listeners; media/RTC release proceeds immediately.

Source review only: browser downloads, actual codec/MIME support, last-Blob delivery, mobile capability, worker activation/replacement, cross-tab isolation and disk outcomes have not been run in this round.
